# ADR-0033: Login is core

**Status:** Accepted — supersedes the login clause of
[ADR-0025](0025-the-site-wires-its-own-extensions.md); the rest of that record
stands

**Date:** 2026-08-16

## Context

ADR-0025 sent mail, login and session policy to the site's own `init`, on the
grounds that none of them is an app: two register no blueprint and
flask-security brings its own, so dressing any of them as a `SiteApp` would
mean inventing a blueprint to satisfy a contract built around having one.

That reasoning is still correct about what login *is not*. It said nothing
about who should own it, and the answer drifted. podpack came to assert
almost all of login without shipping any:

- `ADMIN_ROLE = "admin"` is podpack's constant.
- `/_status` is guarded by an `admin` predicate whose shape podpack defines.
- The boot check calls `datastore.find_role(ADMIN_ROLE)` — podpack reaching
  into flask-security's datastore to warn that nobody can read its own report.
- The README devotes a section, *The first administrator*, to three
  flask-security commands, and `creating-a-site.md` a numbered step.

What was left to each site was the twenty-four lines of `models.py` that turn
those assertions into a working login. Identical twenty-four lines, in every
site that wrote them. A default nobody had factored out is not per-site
wiring.

The cost showed up three times in one afternoon. holdenweb.com's `/_status`
answered 404 to its owner because the `admin` role had never been created,
and nothing said why. The lab and podpack-demo can never answer it at all —
their site package is podpack itself, or a demo with no login, so no operator
exists and none can — which meant the README's Quick start documented a
`curl` that has never worked and never will. And a warning added to explain
the first of those would have nagged the other two for ever about a condition
that is permanent and correct there.

## Decision

flask-security is a podpack dependency, and `podpack.auth` ships the `User`
and `Role` models, the datastore, the `Security` wiring and `is_admin`.
`create_app` installs it, and `admin` now defaults to `auth.is_admin` rather
than to nobody.

This is [ADR-0029](0029-postgresql-is-required-mongodb-is-optional.md)'s
argument one layer up: **a thing the framework's own endpoints require is not
optional**, and calling it optional produces sites that cannot do what the
framework documents. That record flipped PostgreSQL from optional to required
when a `--services mongodb` site was produced that could not boot. This is the
same shape with the same evidence.

Mail and session policy stay where ADR-0025 put them. They are genuinely
per-site: a site chooses its own mail server, or sends no mail at all. A site
that sends mail may pass `PODPACK_MAIL_UTIL_CLS` so that a delivery failure is
reported rather than raised through flask-security's uncaught views.

## Consequences

Every site now has `user`, `role` and `roles_users`, whether it wanted a login
or not. podpack-demo gains three tables it does not use, which is the price of
the lab and the demo being able to show `/_status` at all — they never could
before.

podpack declares tables for the first time, so it needs an owner for them.
Attribution is by defining module and walks the app list, which podpack is not
on, so all three would have been reported by `unclaimed.tables` — the feature
[ADR-0032](0032-tables-are-claimed-not-prefixed.md) added days earlier — as
answered for by nobody. `create_app` records them as podpack's before the apps
install, which also means an app claiming `user` now collides with the
framework rather than with whichever site got there first.

Migrations stay as they are, under
[ADR-0009](0009-one-alembic-history.md): podpack's models enter the site's
metadata and each site's own history carries the revision creating them. That
is already what holdenweb.com's `69b5755e12e0` does, and existing sites are
stamped past it, so nothing has to be re-run. A site adopting this gains three
tables in its next autogenerated revision.

`db` moved to `podpack.database`. `auth` defines models against it and is
imported by `__init__`, so `from . import db` there reached into a package
still executing its own body — which happens to work and which mypy correctly
refuses to type. `podpack.db` is unchanged for everyone else.

## Alternatives considered

- **An optional core service**, reusing the
  [ADR-0028](0028-core-services-are-overlays-the-site-chooses.md) machinery
  built for MongoDB: `podpack[auth]`, declared in `[site] services`. It fits
  the existing architecture exactly and would have kept podpack-demo
  login-free. Rejected because it repeats precisely what ADR-0029 corrected:
  `/_status`'s guard needs login, so a site declining it gets a framework
  endpoint that cannot work, and the framework has no way to say so beyond a
  warning that would never stop firing.
- **Leaving it with the site and improving the documentation.** The
  documentation was not the problem; it was already correct and already
  detailed. Three sites had followed it and one of them still locked its owner
  out.
- **Shipping a migration inside the package** for podpack's own tables.
  Guarantees every site has the same schema, and needs `version_locations`
  plus branch labels — which ADR-0009 rejected, for reasons that have not
  changed.
- **Making the models extensible now**, with a documented hook for a site to
  add fields to `User`. Deferred rather than rejected: no site here needs it
  yet, and guessing at the shape of an extension point nobody has asked for is
  how frameworks acquire the wrong one. flask-security's mixins remain
  available to a site that subclasses them, which is the escape hatch until
  there is a real requirement to design against.
